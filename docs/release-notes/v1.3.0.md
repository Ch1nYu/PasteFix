v1.3.0 adds an explicit processing mode selector and fixes two clipboard write-back failures that had been failing silently since v1.2.0.

## What changed

**1. Processing Mode Selector**
- The tray menu now has a **處理模式** submenu with two modes:
  - **智慧續行 (Smart Continuation)** — the default and unchanged behavior: dedent, margin repair, and continuation joining that preserves multi-line structure.
  - **強制單行 (Force Single Line)** — trims each physical line and joins every non-empty line with a single space.
- The mode is persisted in `%APPDATA%\PasteFix\settings.json` as `Mode` (`0` = Smart Continuation, `1` = Force Single Line) and survives restarts. A missing or unrecognized value falls back to Smart Continuation, so upgrading from v1.2.0 is safe.
- Exactly one transformer runs per clipboard update; the two modes are never chained.
- Force Single Line is intentionally destructive for Python, YAML, here-strings, heredocs, and any block holding more than one command. It is an explicit opt-in.

**2. Empty Cleaning Result No Longer Crashes**
- A copy containing nothing but whitespace reduced to an empty string, which was then written back — `Clipboard.SetText` rejects an empty string with `ArgumentNullException`.
- Six of these are in `pastefix.log` between 2026-09-03 and 2026-10-10.
- An empty result is now treated as "nothing to clean": the clipboard keeps exactly what was copied.

**3. Clipboard Contention Is Now Reported Instead of Swallowed**
- When another process holds the clipboard open, `Clipboard.SetText` throws `ExternalException` (`0x800401D0`, `CLIPBRD_E_CANT_OPEN`) after its internal ten retries. Thirteen of these are in `pastefix.log` between 2026-09-11 and 2026-10-08.
- The write is now wrapped in a `try`/`catch` that logs the failure and shows a warning balloon, so a paste that went out uncleaned is visible rather than mysterious. No retry is added: `SetText` already waited a full second before throwing.

**4. AutoMonitor Off Now Stops In-Flight Work**
- Toggling AutoMonitor off mid-debounce cancelled neither the pending tick nor its notification. The pending clean is now dropped when monitoring is disabled.

## Root cause of the silent failures

`Program.cs` installs an `Application.ThreadException` handler so a single clipboard error cannot kill the tray. The side effect was that all 19 of the exceptions above were logged and then forgotten: the tray kept running and the only symptom was a paste that had not been cleaned. Both crashes were pre-existing in v1.2.0 — the v1.3.0 changes sit on the same `CleanClipboard` path, which is how they were found.

## Tests

- 98 unit tests, including new coverage for the write-back decision (empty result, unchanged text, whitespace-only input in both modes) and for mode dispatch and settings parsing.
- `tools/manual-test.ps1` end-to-end clipboard smoke test.
- `tools/toggle-test.ps1` runtime regression test covering AutoMonitor off, both modes, and mode persistence across a restart. The script restores the original `settings.json`, clipboard content, and running tray process on exit.

## Install

Unchanged — run `PasteFix.exe`, self-contained single file, not code-signed (SmartScreen: *More info* → *Run anyway*).
