## 階段 2：AutoMonitor 去留（計畫第四節的未決事項）

**決定：保留 AutoMonitor，只做 `Dedent`。**

背景：原本 Q17 決定「AutoMonitor 做無損轉換」時，無損轉換有兩件事（行尾 + 共同縮排）。行尾轉換被實測否決之後只剩一件，所以「為了一個 dedent 而常駐監聽剪貼簿值不值得」需要重新判斷。

理由：

1. **它是使用者明確要的東西。** 使用者問過「為什麼不能綁在原本的 Ctrl+V 上面」。AutoMonitor 正是讓平常的 Ctrl+V 直接可用的機制——修復發生在**複製**的瞬間，所以貼上時剪貼簿已經是好的。刪掉它就等於回答「不行，你每次都得按 Alt+V」。
2. **它通得過驗收標準 (c)**（每條規則都要對得上實際遇過的情境）。使用者原話：「它會有前面的空白……影響到我整個腳本的輸入」。這就是 `Dedent` 的情境。
3. **風險已經結構性消除。** `Dedent` 保留相對縮排，Python / YAML / here-string 都不受損；有損的續行合併只走 Alt+V。BUGREPORT 那些災情的成因（無條件語意清洗）不復存在。

此決定是可逆的：若日後覺得多餘，刪掉 `_window.SetClipboardListening` 那條路徑即可，`Dedent` 仍會透過 Alt+V 生效。

## 階段 3：重寫 `Normalizer.cs`

刪除的規則與對應的公開成員：`FenceLine()`、`ShellPrompt()`、`PowerShellPrompt()`、`AnyPrompt()`、`NormalizeLineEndings()`，以及 `multiPrompt` 的計算、早退、prompt 剝除、`#` 過濾、`TrimEnd()`。

新的公開介面只有兩個：

```csharp
public static string Dedent(string input);     // 去除共同縮排（結構保留）
public static string Normalize(string input);  // Dedent + 合併續行
```

實作要點：

- **行尾**：偵測輸入第一個分隔符（`\r\n` / `\n` / `\r`）並原樣重組，不做任何轉換。
- **共同縮排**：取所有非空行的最長共同**前綴字串**（不是字元數），因此 tab 與空格混用時不會算錯；共同前綴為空就完全不動。
- **續行標記**：`\`、反引號、`&&`、尾端 `|`。前兩者在合併時被吃掉，後兩者保留。
- **三層守衛**：括號深度為 0、不在引號字串內、不在 here-string / heredoc 內。

### 自我測試抓到的兩個缺陷

單元測試第一次就全綠，所以另外做了兩輪獨立驗證，兩輪都抓到單元測試漏掉的東西。

**缺陷 1 — Windows 路徑被當成 bash 續行**（行為 sweep 抓到）

```
IN   |cd C:\temp\
IN   |dir
NORM |cd C:\temp dir          ← 錯誤合併
```

根因：續行標記只檢查「行尾是不是 `\`」，沒有檢查前面是什麼。修法是要求標記**前面必須是空白**——真正的續行一定寫成 `command \`，而路徑是 `C:\temp\`。這個約束順帶也擋掉了 ` ``` ` 圍欄（最後一個反引號前面是反引號）和 `\`，比原本的 lookbehind 更乾淨。

**缺陷 2 — 續行後接空行，正是 BUGREPORT 的 `EmptyPipeElement`**（同一輪 sweep 抓到，由冪等性檢查告警）

```
IN   |Get-Process |
IN   |
IN   |Select-Object -First 3
NORM |Get-Process |            ← 空行被當成空段落吸收，留下尾隨空格
NORM |Select-Object -First 3   ← 管線還是斷的，而且不冪等
```

修法：累積續行的過程中直接跳過空行。續行標記與指令其餘部分之間的空行沒有任何意義，而它正是把 `Get-Process |` 變成 `An empty pipe element is not allowed.` 的原因。**這個缺陷如果沒被抓到，等於整個專案宣稱要修的頭號案例其實沒修好。**
