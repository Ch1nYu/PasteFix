## 起點：這工具「還不夠實用」

使用者的一句話開始了這輪工作：

> 現在來討論怎麼優化這個專案的功能，目前還不夠實用

盤點後收斂成三個缺口，全部有 log 或原始碼證據：

| 缺口 | 證據 |
|---|---|
| **無可觀察性** | `%APPDATA%\PasteFix\pastefix.log` 有 1233 行，涵蓋 2026-08-07 → 2026-10-12。其中 `CleanClipboard changed=True` 只有 **27 次，全部落在 2026-08-08 ~ 08-20**。2026-09-07 之後的永久記錄只有開機、監聽器、模式切換、例外。**成功清洗 0 筆。** 使用者無從得知工具到底幫上忙了沒有。 |
| **無退路** | `Clipboard.SetText` 覆蓋原稿後原文即消失。這解釋了 AutoMonitor 的反覆開關（08-10、08-13、08-16、08-18、08-27 都有 `AutoMonitor -> False`）——無法反悔的自動行為只能靠關掉避險。 |
| **無鍵盤入口** | 現行原始碼 `rg "RegisterHotKey\|SendInput\|keybd_event\|SetWindowsHookEx"` 為 **0 筆**。唯一入口是系統匣的兩層選單。 |

第三點的考古發現：v1.2.0 同時砍掉了 Alt+V 熱鍵**與**輸入模擬（`SendInput`），但那是兩個獨立的決定。禁令針對的是合成輸入（曾造成 WezTerm 開出數十個 tab），而 `RegisterHotKey` 只是請 Windows 送 `WM_HOTKEY`，不送鍵、不 hook。當時把兩件事一起砍掉了。

## 四個切片

| 切片 | 內容 | 檔案 |
|---|---|---|
| A1 | 每次成功清洗寫一行永久記錄（尺寸、行數、剝掉的容器，永不寫文字） | `ClipboardSummary.cs`、`TrayApplication.cs` |
| A2 | 「還原上一次清洗」——只存在記憶體，剪貼簿已換過內容則拒絕 | `LastClean.cs`、`TrayApplication.cs` |
| B | 容器剝除：markdown fence、重複的 prompt gutter、行號 gutter | `ContainerStripper.cs` |
| C | 全域熱鍵 Ctrl+Alt+Shift+V，預設關閉 | `HotkeyWindow.cs` |

### B 與 2026-08-09 判決的區別

2026-08-09 移除的是**逐行猜測哪一行是指令**的規則（對 YAML、Python 造成災情，見 `BUGREPORT-2026-08-08.md`）。`ContainerStripper` 的設計刻意不同：**沒有任何規則判斷個別行的語意**。包裝要嘛確證涵蓋整份複製（fence 開在首行、閉在末行、中間沒有 fence 形狀的行；每個非空行同一種 prompt 風格；編號連續），要嘛就不是包裝，原文 byte for byte 回傳。

**可見的失誤永遠優先於無聲的破壞：**

- `1. ` / `1) ` 是 markdown 有序清單語法，不是 gutter 語法，永不剝除
- 單行 `$ npm install` 不剝除（gutter 要有兩行才有側邊）
- 未閉合、沒包住全部、中間夾 fence 形狀的行，一律不動
- 混用 prompt 風格不動

### A2 的設計修正

`LastClean` 初版只有 `_before` 和語意反了的 `Matches()`。必須同時記住清洗後的結果才能判斷剪貼簿是否還停在該次清洗上，故改為 `_before`/`_after` 兩欄與 `StillOnClipboard`。

`Take()` 的初版設計會在剪貼簿暫時被佔用時**永久吃掉 undo 機會**（先清除再寫回，寫回失敗就沒了）。改為 `Before` 唯讀屬性 + 寫回成功後才 `Clear()`：「a clipboard that was busy for a moment does not cost the user the only way back.」

### C 的設計邊界

`HotkeyWindow` 的 XML 註解明載：**這不是 2026-08-16 禁掉的輸入模擬。** `RegisterHotKey` 是請 Windows 在按下時送 `WM_HOTKEY`，不送鍵、不裝 hook；handler 走的是選單已經在走的同一條 `CleanClipboard` 路徑。註冊失敗（組合鍵被其他程式佔用）時選單項顯示為未勾選，設定值保留供下次啟動重試。

## 後續：模式問題的證據基礎（commit `334d377`）

使用者接著問：

> 是說現在有沒有辦法把智慧和單行整合起來，但是我當初分開就是因為很難分辨，什麼時候我需要單行甚麼時候不需要，情況很多但是我沒有紀錄

log 考古發現：**32 次模式切換，2026-09-07 → 2026-10-07。16 次切到 SingleLine，16 次切回 Smart。** 停留時間中位數約 20 分鐘，其中 **5 次在一分鐘內來回**——代表手動切換常常是在**修正用錯的模式**，而不是表達長期偏好。

最長的一次 SingleLine 持續 **1 天 6 小時 44 分**，所以不是「永遠不該用單行」。

結論：整合的前置條件是**證據**，不是設計。若直接合併，等於用猜測取代那 32 次人工判斷。

因此本輪最後一個 commit 只做一件事：**把模式寫進永久 log**，包含「看了但沒動」的路徑——那條才是對照組，它證明另一種模式也沒事可做。

```
cleaned: len=17->17 lines=2->1 containers=none mode=SingleLine
cleaned: len=29->17 lines=4->2 containers=Fence mode=SmartContinuation
clean skipped, no change needed: len=41 mode=SmartContinuation
```

`lines=A->B` 是判別點：`2->1` 是需要壓成一行的複製，`4->4` 是本來就好的，`clean skipped` 是兩種模式都不會動的。

**行為完全沒動**：沒有新模式、沒有自動偵測、沒有改任何轉換邏輯。只是讓既有的判斷留下痕跡。
